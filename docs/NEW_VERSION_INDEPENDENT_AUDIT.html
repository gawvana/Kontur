«Контур»: независимая проверка новой версии

Проверен архив Kontur(1).zip, 4 октября 2026 года. Проект не готов к публичному запуску.

Код заметно расширен: появились приватные контакты, трёхшаговая форма опыта, административные решения, апелляции, поддержка и таблицы новых сущностей. Но основной сквозной сценарий по-прежнему не работает. Особенно опасны пропуск второго фактора для новой сессии сотрудника, публикация непроверенных дополнений и отсутствие последствий отмены решения. Перенос на Supabase сейчас дополнительно блокируют PostgreSQL-миграции.

Утверждение docs/STATUS.md «все требования полностью реализованы и подтверждены тестами» опровергнуто кодом и воспроизведениями. Исходные 62 теста проходят, но это преимущественно прежние регрессии. Зелёная сборка не подтверждает согласованность UI и API.

1. Что именно проверено и где границы

  • ZIP прочитан из предоставленного локального вложения. Исходный архив не изменялся. SHA256: de70aa3ba034cb5f3f78d847ac8fca3be7376e6de16f39611ac0359365ef3d32.
  • В архиве 28 985 записей, около 455,7 МиБ распакованного содержимого. Для анализа выделены 156 файлов без Windows venv, node_modules, кешей и Git-объектов; 45 Python-файлов проверены на синтаксис.
  • Изучены все транспортные обработчики API/бота/worker, модели, схемы, миграции, четыре страницы Mini App, административный интерфейс, конфигурации и документы. Реализация сопоставлена с полной спецификацией и прежней версией ZIP.
  • В отдельных тестовых БД воспроизведён 41 API-шаг. Сотрудники и Subjects в проверках созданы тестовыми фикстурами: это не доказательство существования пользовательского bootstrap/идентификации.
  • В Chromium выполнены реальные обращения к локальному API и мигрированной изолированной SQLite. Проверены поиск, сохранение текста каталога, фильтр каталогов, потеря черновика, создание обращения, очередь admin, темы, reload и неудачный logout. Telegram SDK и подписанная initData синтетические, только для локальной проверки; production-auth не изменялся.
  • Просмотрены мобильные скриншоты 390×844, проверено отсутствие горизонтального переполнения главной и профиля на доступных viewport, профиль дополнительно на 360 и 430 px; admin проверен на 1280×900. Это эмуляция размера экрана, не настоящий телефон и не Telegram WebView. Клавиатура устройства, все модальные состояния и все ширины всех экранов не сертифицированы.
  • PostgreSQL SQL проверен исполнением в PGlite / PostgreSQL 18.3 WASM, отдельно от SQLite. Это подтверждает приведённые ошибки SQL, но не заменяет подключение к живому Supabase/PostgreSQL, проверку драйвера, пулов, блокировок и нагрузки на вашем хостинге.
  • Полный Docker-стек, настоящий Telegram, Redis/Celery broker, S3, INFRLO и Vercel не запускались: отсутствуют настроенная инфраструктура и реальные доступы. Тестовые серверы остановлены в finally.
  • Замер RSS процесса API в этой среде недоступен: статус дочернего процесса не виден через /proc. Достаточность 512 МБ RAM не подтверждена, выдуманных метрик FPS/p95/памяти в отчёте нет.

4. Подтверждённые дефекты: сначала блокеры выпуска

Здесь P1 — серьёзная ошибка безопасности, основного сценария или развёртывания; P2 — неполная функция, устойчивость, удобство либо документация. Приоритет задан для полной версии «Контур», а не для демонстрационного макета. Отсутствие находки P0 не означает отсутствия неизвестных критических уязвимостей.

N01 · P1 · PostgreSQL-миграция падает на boolean default

Источник: services/api/alembic/versions/full_features.py, добавление is_2fa_enabled и других boolean-полей.

sa.text("0") компилируется в BOOLEAN DEFAULT 0, а sa.text("1") — в integer default 1. Исполнение оригинального alembic upgrade head --sql в PostgreSQL дало SQLSTATE 42804: column "is_2fa_enabled" is of type boolean but default expression is of type integer.

Последствие: нельзя применить полную миграцию к PostgreSQL/Supabase. Генерация SQL с нулевым exit code и SQLite-тест не обнаруживают это. Исправление: переносимые boolean defaults, затем реальный upgrade и сохранение старых данных на целевом PostgreSQL.

N02 · P1 · Новые PostgreSQL enum не согласованы с ORM

Источник: full_features.py, db/models.py.

Для диагностики только в памяти заменены boolean defaults; файлы проекта не правились. После этого миграция исполнилась, но casestatus сохранил только {PENDING,APPROVED,REJECTED}. SELECT 'DRAFT'::casestatus дал 22P02. Типы experiencetype, casevisibility, catalogmemberrole, ожидаемые native Enum в ORM, не созданы — 42704. Другие новые Enum тоже требуют согласования: миграция использует String там, где ORM объявляет PostgreSQL Enum.

Исправление: выбрать единую стратегию native enums либо строк с ограничениями, явно обновить старый casestatus, проверить bind-параметры asyncpg и alembic check на настоящем PostgreSQL. Одной замены default недостаточно. Документация PostgreSQL: boolean, ALTER TYPE.

N03 · P1 · Второй фактор не защищает новую сессию сотрудника

Источник: api/deps.py:53, auth.py:245, модель Session.

Проверяется глобальный User.is_2fa_enabled, а не факт подтверждения TOTP в текущей сессии. Для аккаунта с этим флагом новая обычная Telegram-сессия сразу получила 200 /admin/dashboard, без кода. То же подтверждено административным интерфейсом: сразу показан бейдж «2FA Активен» и панель.

Последствие: получение первого фактора/действующей сессии сотрудника даёт административный доступ без дополнительной проверки. Исправление: хранить проверку второго фактора в конкретной сессии, срок step-up, отзывать её при чувствительных изменениях; отличать «фактор настроен» от «эта сессия подтверждена».

N04 · P1 · Настроенный второй фактор можно заменить без старого кода

Источник: auth.py:220.

POST /auth/2fa/setup доступен обычной действующей сессии, заменяет секрет, удаляет прежние recovery codes и выдаёт новые. Нет требования текущего второго фактора, отдельного pending-секрета и проверки активного фактора перед заменой. Для сотрудника с включённым 2FA это дало 200; новый recovery code также принят с 200, без подтверждения старого фактора и нового TOTP.

Исправление: отдельные initial enrollment, verification, rotation и recovery; step-up для смены включённого фактора, атомарное погашение recovery-кода, ограничения попыток и журнал. TOTP-секрет сейчас хранится открытым текстом; включить защиту ключом вне БД. Нет готового bootstrap первого owner.

N05 · P1 · Поиск вызывает белый экран Mini App

Источник: subjects.py:103, Check.tsx:128, интерфейс SubjectSearchResponse в api.ts.

API возвращает list[SubjectResponse], UI читает {items,total} и обращается к data.items.length. Реальный поиск @audit_contact в браузере вызвал Cannot read properties of undefined (reading 'length'), React очистил корень приложения. Ошибка происходит и для пустого массива, так что ветка сохранения неизвестного контакта с экрана проверки тоже ломается.

Исправление: единый фактический DTO, типы из OpenAPI и контрактная проверка ответа; ErrorBoundary как дополнительная защита от белого экрана, не замена правильному контракту. Обещанный поиск по ID также не реализован: серверный нормализатор отвергает число.

N06 · P1 · Карточка с опубликованным обращением падает на ORM lazy loading

Источник: subjects.py:164, Case.responses в db/models.py.

После публикации связанного обращения GET /subjects/1/card вызвал MissingGreenlet на hasattr(c,"responses")/len(c.responses): обычная lazy relationship пытается делать async IO из синхронного обращения к атрибуту. Для пустой карточки этого может не быть.

Исправление: явная eager-загрузка разрешённых ответов либо отдельный запрос exists/count, ограничения размера истории, повторный тест карточки с обращениями и ответами.

N07 · P1 · Отправка формы не передаёт обращение в рабочую очередь

Источник: Cases.tsx:37, cases.py:61, admin.py:80–102.

Mini App вызывает legacy POST /cases, который сохраняет PENDING. /admin/cases по умолчанию показывает SUBMITTED/IN_REVIEW; принятие решения также не допускает PENDING. /cases/{id}/submit принимает только DRAFT и для этого обращения возвращает 404. При этом UI говорит «успешно … отправлено на рассмотрение».

Браузер: создано обращение #1; dashboard показывает 1 «На рассмотрении», вкладка «Обращения (0)» и текст «Все поступившие обращения рассмотрены».

Исправление: одна договорённая цепочка draft → submit → очередь; корректный переход для legacy-данных и правдивый success после серверного submit. Проверить новый пустой аккаунт до административного решения без ручной правки БД.

N08 · P1 · Конвейера доказательств нет, worker имитирует READY

Источник: worker/tasks.py:8–26, маршруты API и форма Cases.

Нет пользовательского endpoint загрузки/скачивания, file input, подписанных загрузок, создания Evidence из разрешённого файла, MIME/magic-проверок, лимитов, S3-клиента, обезличивания и настоящего сканирования. Запрос к ожидаемому пути /cases/{id}/evidence получил 404. Worker не читает файл: отправляет {"status":"READY","storage_key":...} в несуществующий /internal/evidence/{id}/processed.

Исправление: реальные upload/state/storage ACL, quarantine, проверка содержимого, приватный оригинал и отдельная безопасная производная. При недоступном сканере файл остаётся непубликуемым. Замена NotImplementedError на симуляцию — регресс относительно честного отказа.

N09 · P1 · Публикация допускается без доказательств и подтверждённой личности

Источник: admin.py:104–118, admin.py:220, cases.py:132.

Черновик без Subject, доказательств и достаточных деталей принят и опубликован через 200 APPROVE. Созданный фикстурой файл application/octet-stream в PENDING без redacted copy одобрен с READY и is_published=true. Это воспроизведение отсутствующих guards, не утверждение, что пользовательский upload уже работает.

Исправление: отдельные обязательные основания идентификации и допустимости публикации, подтверждённая безопасная версия материалов, ожидаемая версия решения, ограничения конфликтов. Для непроверенного username допускается приватное сохранение, не публичная привязка обвинения.

N10 · P1 · Дополнение публикуется до проверки и остаётся видимым после отказа

Источник: cases.py:214–238, admin.py:109, case_visible.

После APPROVE автор сделал supplement с новым result_description и violation_details. Case перешёл в IN_REVIEW, но сохранил PUBLISHED; третье лицо немедленно прочитало UNREVIEWED PUBLIC CHANGE и UNREVIEWED SENSITIVE DETAILS с 200. Затем модератор отклонил новую версию: статус REJECTED, видимость по-прежнему PUBLISHED, новый текст по-прежнему доступен.

Исправление: хранить неизменяемую опубликованную версию отдельно от pending revision; не изменять её поля до решения. Переводы status и visibility должны иметь согласованные guards и транзакционные последствия. Безопасное скрытие не должно зависеть только от UI.

N11 · P1 · Апелляция меняет запись апелляции, но не исходное решение

Источник: admin.py:157–199.

Отмена OVERTURNED вернула 200, однако Case остался APPROVED/PUBLISHED, исходные материалы читались третьим лицом. 6. Что исправлять в каком порядке

  1. Не публиковать текущую версию для реальных обращений. Сначала устранить N03/N04 и N09–N13/N28: права staff-сессии, опасную публикацию, версии, апелляции, авторство ответов и публичные DTO. Сохранить прежние проверки подписи/приватности.
  2. Подготовить настоящую базу: N01/N02, затем fresh upgrade, upgrade со старыми данными и enum/DDL/driver проверки на отдельном PostgreSQL/Supabase test project. Не прогонять разрушительные проверки на production.
  3. Починить основной путь: N05/N06/N07/N14/N15. Новый пользователь → приватный контакт → проверенная связь → полноценный опыт и материалы → submit → модерация → карточка/репутация → ответ → независимая апелляция.
  4. Завершить доказательства и jobs: N08/N23/N24/N25, приватное storage, настоящий scanner/redaction, outbox, Telegram-сценарии и durable retries. Статусы «не реализовано» честнее симуляции, но задача полной версии требует реализации.
  5. Довести каталоги и формы: N16–N22/N26/N27, shared ACL, фильтры, архив, безопасное сохранение/повторы, autosave, logout и квоты. Добавить meaningful integration/browser regressions на найденные дефекты.
  6. Сверить весь UI и реальный deploy: N29–N32 плюс отсутствующие функции таблицы. Vercel/API routes, настройки INFRLO, Supabase connectivity, broker/worker, память и нагрузка, backup/restore, свежая документация. В финале повторить релевантные тесты и сквозной набор.

Отдельный тестовый Telegram-бот и отдельная БД нужны для живой приёмки. До их появления можно и нужно завершить код, локальные guards, реальные adapters и тестовые сценарии; отсутствие токена не объясняет отсутствующий импорт/экспорт или неверный DTO поиска.

7. Что убрать, что сохранить

Убрать из production-поведения: фиктивный READY, logging-only «доставку», сообщения о submit/revoke без подтверждённого действия, глобальный флаг 2FA как пропуск сессии, единый сырой DTO публичного и авторского просмотра. Заглушки бота заменить реальными обработчиками, не пустыми success.

Убрать из текущей документации/передачи: ложный «финальный релиз», непроверенные Done/p95, старые команды и устаревшее описание API; из исходного ZIP — dependency folders и случайные тестовые БД. Исторические отчёты можно оставить явно отдельным архивом.

Сохранить: проверку Telegram, отсутствие дефолтного JWT-секрета, server session/revoke, базовые object ACL, регрессии, работающий первый приватный контакт, новый дизайн-референс и пользовательские данные. Не исправлять права открытием всех Subjects и не уничтожать заметки каскадом.

Итог: это расширенная, частично работающая версия с реальными улучшениями, но не законченное приложение. Обязательные условия выпуска — устранить подтверждённые блокеры, реализовать отсутствующие процессы и пройти живой сквозной сценарий на выбранной инфраструктуре. Заявление «исправлены абсолютно все баги» на основании этого аудита делать нельзя.
